# 태스크 63 — 터미널 입력이 밀리고 씹히는 원인과 수정 (입출력 전송로)

> 상태: **구현 완료 · 합격선 5/5 통과** (2026-09-08) · 대상: gitpervisor · 근거: **실측**(CDP,
> dev 디버그 빌드, Windows 11 / WebView2 152.0.4191.66 / pwsh ConPTY, 120×40) ·
> 선행: 태스크 16(PTY 설계), 33(번들 ConPTY) · **Rust + 프론트 양쪽 변경**
>
> 결과 요약은 §7. 벤치는 `tests/bench/terminal-io.mjs` — 같은 스크립트로 언제든 다시 잰다.

## 1. 증상

> "무슨 일이 있어도 터미널 세션에 타이핑하면 무조건 잘 받아서 입력되어야 하는데
> 지금 타이핑이 엄청 느리고 씹히고 렉걸리는 느낌이다."

관찰되는 모양은 **균일한 느려짐이 아니라 간헐적 정지**다. 조용할 때는 멀쩡하고, 옆 패널에서
Claude Code·빌드 로그가 흐르는 동안 입력이 수백 ms 멈췄다가 한꺼번에 쏟아진다. 터미널에는
로컬 에코가 없으므로(글자는 전부 셸이 되돌려준 것) 사용자가 보는 지연 = **왕복 전체**다.

## 2. 실측

전부 `tests/e2e/lib/cdp.mjs`로 실행 중인 dev 앱에 붙어 `__TAURI_INTERNALS__`를 직접 구동해 잰
값이다. UI는 건드리지 않고 `term_open`/`term_write`/`term_close`만 썼다.

### 2.1 키 한 벌 왕복 (`term_write` 직렬 60키)

| | 조용할 때 | **옆 터미널이 출력 중** |
|---|---|---|
| p50 | 4.9 ms | 4.8 ms |
| p90 | 7.7 ms | **48.1 ms** |
| max | 12.7 ms | **993.4 ms** |
| 지속 타이핑 | 187 키/초 | **26 키/초** |

p50은 그대로인데 p90·max만 터진다 — **머리 막힘(head-of-line blocking)**이지 전반적 부하가
아니다. 한 번의 993 ms 정지 동안 사용자가 친 키는 전부 뒤에 줄을 서고, 그다음 한꺼번에 나온다.
이것이 "씹힌다"의 정체다.

이 수치는 **터미널 2개뿐인 dev 앱**에서 나왔다. 사용자의 설치본은 13개다(메모리: 머신 부팅 기준선).

### 2.2 출력 전송로 처리량

| 시나리오 | 메시지 | 바이트 | 청크 p50 | 총 KB/s | **메시지/초** |
|---|---|---|---|---|---|
| 1 터미널, 3 MB 일괄 | 5,801 | 3,002,061 | 256 B | 1,731 | **3,345** |
| **3 터미널 동시**, 각 3 MB | 12,797 | 7,774,575 | 256 B | 1,354 | **2,228** |

**터미널을 늘리면 총 처리량이 오히려 줄어든다.** 병목은 ConPTY(생산자)가 아니라 **모두가 공유하는
한 자원**이다. 앱 전체가 초당 약 2,000~3,300개 IPC 메시지에서 포화한다.

청크 p50이 **256 B**인 것도 핵심이다(느린 셸 출력에서는 47 B까지 내려간다). 리더의 64 KB 버퍼는
한 번도 차지 않는다 — `read()`는 "그 순간 있는 만큼"만 돌려주기 때문이다.

## 3. 원인

네 겹이 겹쳐 있고, **위 두 개가 지배적**이다.

### 3.1 PTY 출력 1청크 = IPC 메시지 1개 (지배적)

`commands/terminal.rs:205-231`의 리더 스레드는 `read()`가 돌려준 것을 **그대로** `Channel::send`
한다. ConPTY가 256 B씩 주므로 1 MB 출력 = 약 4,000 메시지다.

`Channel<Vec<u8>>`은 serde로 **JSON 숫자 배열**이 되고(`[27,91,50,...]`, 원시 바이트의 약 3.5배),
tauri는 그것을 payload 길이에 따라 둘 중 하나로 보낸다
(`tauri-2.11.2/src/ipc/channel.rs:152-180`):

- 8,192자 미만(= 원시 약 2.3 KB 미만) → `webview.eval(...)`에 **JS 소스 문자열로 인라인**
- 그 이상 → `ChannelDataIpcQueue`에 넣고 `eval`로 **fetch를 한 번 더** 태운다

그리고 `webview.eval`은 리더 스레드(= 메인 스레드가 아님)에서 불리므로
`tauri-runtime-wry-2.11.2/src/lib.rs:1850` → `send_user_message`(`:235-255`)를 지나
**이벤트 루프에 UserEvent로 게시**된다. 즉 **PTY 청크 하나마다 메인 이벤트 루프 태스크 하나**다.

64 KB 버퍼(`terminal.rs:206-208`)의 주석은 "Channel send 횟수를 1/8로 줄인다"고 적고 있는데,
**그 최적화는 실제로 작동하지 않는다.** 버퍼 크기는 상한일 뿐이고 `read()`는 있는 만큼만 돌려준다.
줄여야 하는 것은 버퍼 크기가 아니라 **시간축 합치기**다.

### 3.2 키 입력이 그 출력과 같은 펌프를 탄다 (지배적)

`invoke()`는 커스텀 프로토콜로의 `fetch` POST다(`tauri-2.11.2/scripts/ipc-protocol.js:22-45`).
WebView2에서 그 요청은 `WebResourceRequested`로 **메인 스레드에서** 처리된다 — 3.1의 eval 큐와
**같은 줄**이다. 출력이 초당 3,000개 태스크를 밀어 넣는 동안 도착한 `term_write`는 그 뒤에 선다.
2.1의 p90 48 ms / max 993 ms가 이것이다.

### 3.3 프론트가 키를 **왕복 완료까지** 직렬화한다 (증폭기)

`lib/terminal-engine.ts:80-96`의 `ptyWrite`는 `writeChains`로 키마다 이전 `invoke`의 **응답까지**
기다린 뒤 다음을 보낸다. 순서 보장이 목적이고 그 자체는 옳다(`:31-37`의 주석대로, `term_write`가
`#[tauri::command(async)]`라 도착 순서 ≠ 실행 순서다).

문제는 **정지 1회의 비용이 대기 중인 키 개수만큼 곱해진다는 것**이다. 993 ms 정지 중에 8키를
쳤다면 그 8키는 993 ms 뒤부터 다시 하나씩 왕복한다. 187 → 26 키/초 붕괴가 여기서 나온다.

### 3.4 `term_write`가 **전역** 세션 락을 쥐고 쓴다 (부수적)

`state.rs:35`는 `Mutex<HashMap<String, TerminalSession>>` 하나다. `terminal.rs:296-310`의
`term_write`는 그 락을 잡은 채 `write_all` + `flush`를 한다. 터미널 13개가 락 하나를 두고 다투고,
한 세션의 ConPTY 입력 버퍼가 차서 write가 막히면 **나머지 12개의 키 입력이 함께 막힌다.**
`term_resize`·`term_open`·`term_project`·리더 스레드의 자기 회수도 같은 락이다.

## 4. 설계

### P0 — 출력을 시간축으로 합친다 (`commands/terminal.rs`)

세션마다 **리더 스레드 + 펌프 스레드**로 나눈다.

- 리더: 지금처럼 블로킹 `read()` → `mpsc::Sender<Vec<u8>>`로 넘기기만 한다.
- 펌프: `recv_timeout(FLUSH_MS)`로 모으다가 **`FLUSH_MS`(4 ms) 경과 또는 `MAX_CHUNK`(64 KB) 도달**
  시 한 번만 `Channel::send`. Pacer도 여기로 옮긴다(보내는 지점이 여기 하나이므로).

왜 스레드를 하나 더 쓰는가: `portable_pty`의 리더에는 타임아웃 read가 없다. 폴링으로 흉내내면
CPU를 태우고, 플랫폼별(`poll()` vs 파이프 핸들) 분기가 생긴다. 세션당 스레드 2개(13세션 = 26개)는
전부 대기 상태라 실질 비용이 없고, 기존 "세션당 스레드 1개" 모델의 자연스러운 확장이다.

`FLUSH_MS = 4`인 이유: 지금 키 한 벌 왕복이 p50 4.9 ms다. 4 ms는 **이미 있는 지연보다 작아**
대화형 에코에서 체감되지 않고, 1 MB 출력의 메시지 수를 4,000 → 250 이하로 떨어뜨린다.
값은 상수 하나로 두고 벤치로 조정한다.

**순서·무손실은 그대로다.** mpsc는 FIFO이고 합치기는 이어붙이기뿐이라 ANSI 시퀀스가 잘리지 않는다.
`sink`가 None(의도적 종료)이면 펌프는 버리고 끝낸다 — 지금과 같다.

### P0 — 대용량 청크를 **바이너리 경로**로 보낸다

합치면 청크가 커져 3.1의 JSON 임계(8,192자 ≈ 원시 2.3 KB)를 넘긴다. 그대로 두면 **JSON 숫자
배열을 만들어 fetch로 다시 실어 나르는** 최악 조합이 된다.

`Channel<Vec<u8>>` → `Channel<tauri::ipc::Response>`(`InvokeResponseBody::Raw`)로 바꾼다. 그러면
(`channel.rs:163-180`):

- **1 KB 미만** → `new Uint8Array([...]).buffer`를 eval — 키 에코 같은 작은 것은 지금처럼 1홉
- **1 KB 이상** → fetch 경로로 **ArrayBuffer 그대로** — JSON 직렬화·파싱이 통째로 사라진다

프론트는 `lib/terminal.ts:54-65`의 `attachOutputChannel`이 이미 `new Uint8Array(bytes)`를 하므로
**핸들러 본문은 그대로**고 타입만 `Channel<ArrayBuffer>`로 바뀐다.

### P1 — 입력은 순서만 지키고 **왕복은 합친다** (`lib/terminal-engine.ts`)

`writeChains`의 "이전 응답까지 대기"를 유지하되, **대기 중에 들어온 입력을 문자열로 모아 두었다가
다음 한 번에 보낸다.**

```
inflight[termId] : Promise | null      // 지금 나가 있는 term_write
pending[termId]  : string              // 그것이 끝나기를 기다리는 입력
```

- `inflight`가 없으면 즉시 보낸다(지금과 동일 — 조용할 때 지연 증가 0).
- 있으면 `pending += data`만 하고 끝낸다.
- `inflight`가 풀리면 `pending`이 비어있지 않을 때 통째로 한 번 보낸다.

순서 불변식은 그대로다(이어붙이기는 순서를 보존하고, 한 번의 `term_write` 안에서는 Rust가
`write_all`로 순서대로 쓴다). **정지 1회의 비용이 키 개수와 무관해진다** — 993 ms 정지 후 8키가
8왕복이 아니라 1왕복으로 나간다.

`capturePtyInput`(`prompt-capture.ts:170-186`)은 지금처럼 **모으기 전** 원본 조각마다 호출한다 —
합쳐서 넣어도 `feedInput`은 같은 결과를 내지만, 순서를 바꾸지 않기 위해 호출 지점을 옮기지 않는다.

경계: `pending`에 상한(예: 1 MB)을 두고 넘으면 즉시 강제 전송한다. 거대 붙여넣기가 한 문자열로
무한히 부풀지 않게.

### P2 — 세션 라이터를 전역 락에서 뺀다 (`commands/terminal.rs`, `state.rs`)

`TerminalSession.writer: Box<dyn Write + Send>` → `Arc<Mutex<Box<dyn Write + Send>>>`.
`term_write`는 **전역 락 아래에서 Arc만 복제하고 즉시 락을 놓은 뒤** 그 세션 락으로 쓴다.

```
let w = { terms.lock().get(&id)?.writer.clone() };   // 전역 락은 여기까지
w.lock().write_all(...)?; w.lock().flush()?;         // 세션별
```

`term_resize`(`:341-360`)도 같은 이유로 `master`를 같은 모양으로 뺀다. 6~10줄이고, 터미널 간
머리 막힘이 사라진다.

### P3 — 측정 후 판단 (지금 손대지 않는다)

- **숨은 터미널의 WebGL 컨텍스트.** `WorkspaceTabs.tsx:184-187`은 모든 터미널 탭을 `hidden`으로
  마운트 유지하므로 13개 xterm이 각자 WebGL 컨텍스트를 쥔다. Chromium 상한(~16)에 닿으면 서로
  밀어내고, `terminal-engine.ts:467-486`의 "60초 내 3회 손실 → DOM 렌더러 확정" 폴백이 이미 그
  캐스케이드를 전제로 쓰여 있다(= 실제로 관측된 적이 있다는 뜻). 보이지 않는 탭에서 WebGL 애드온을
  내렸다가 복귀 시 다시 올리는 것이 정답으로 보이지만, **P0~P2 적용 후 다시 재고 나서** 한다.
  → **태스크 69에서 처리**(§3 — attach에서 획득, 뷰 언마운트 1.5초 뒤 반납).
- **`scanAgents`**(`stores/agentActivity.ts:85-98`)가 1.2초마다 살아있는 터미널 전부의 화면을
  `translateToString`으로 읽는다. 13 × 40행이라 메인 스레드에서 무시할 수 없지만 지배적이지 않다.
  필요해지면 `onWriteParsed`로 더티 플래그를 세워 변한 터미널만 읽는다.

## 5. 검증

**정적 검증으로 통과시키지 않는다** — 이 태스크는 처음부터 실측으로 열렸다.

1. **벤치를 저장소에 남긴다.** 위 2.1·2.2를 재는 스크립트를 `tests/bench/terminal-io.mjs`로 커밋한다
   (`tests/e2e/lib/cdp.mjs` 재사용, UI 비접촉: `term_open`/`term_write`/`term_close`만).
   수정 전/후 같은 스크립트로 잰다.
2. **합격선**(수정 후, 조건 동일):
   - 옆 터미널 출력 중 키 왕복 **p90 ≤ 15 ms, max ≤ 100 ms** (현재 48 / 993)
   - 출력 중 지속 타이핑 **≥ 120 키/초** (현재 26)
   - 3 MB 일괄 출력의 메시지 수 **≤ 400** (현재 5,801)
   - 3 터미널 동시 총 처리량이 1 터미널보다 **줄지 않을 것** (현재 줄어든다 — 공유 병목의 지표)
3. **릴리스 빌드에서 다시 잰다.** 위 수치는 전부 **디버그 빌드**다. 병목이 Rust 연산이 아니라
   webview 메시지 펌프라 릴리스에서도 같은 벽이 있을 것으로 보지만, 확인 없이 단정하지 않는다.
4. **회귀**: 기존 e2e 14(터미널) 전 항목, 특히 `#2b`(실제 ConPTY 폭 질의)와 원시 PTY 채널의
   마커 폴링(메모리: e2e 기준선). 한글 IME·붙여넣기·Shift+Enter 경로는 `ptyWrite` **호출부**를
   바꾸지 않으므로 영향이 없어야 하고, 그 사실을 e2e로 확인한다.

## 6. 하지 말 것

- **`writeChains`의 순서 보장을 없애지 마라.** `term_write`가 `#[tauri::command(async)]`인 한
  체인 없이 던지면 "ls"가 "sl"이 된다(`terminal-engine.ts:31-37`의 실사례). P1은 대기를 없애는
  게 아니라 **대기 중 입력을 합치는** 것이다.
- **`FLUSH_MS`를 크게 잡지 마라.** 이 값이 곧 에코 지연의 하한이 된다. 4 ms는 현재 왕복
  p50(4.9 ms)보다 작아서 안전하고, 16 ms를 넘기면 사람이 느낀다.
- **Pacer를 지우지 마라.** 상한이 없으면 무한 출력이 `ChannelDataIpcQueue`에 쌓여 앱이 메모리로
  죽는다(`terminal.rs:40-48`). 펌프로 **옮기되** 예산 계산은 그대로 둔다.
- **`attachOutputChannel`의 "채널 재사용 금지"를 건드리지 마라**(`lib/terminal.ts:37-53`).
  payload 타입만 바뀌고 인덱스 카운터 계약은 그대로다.
- 64 KB 읽기 버퍼를 "더 키우면 낫겠지"로 늘리지 마라 — 3.1대로 크기는 병목이 아니다.

| (같은 회차 1터미널) | 1,731 KB/s | 4,713 KB/s | |

**마지막 두 줄이 진단의 핵심이었다.** 수정 전에는 생산자(터미널)를 3배로 늘리면 총 처리량이
**줄었다** — 공유 자원이 병목이라는 서명이다. 지금은 늘리면 는다. 그 자원이 키 입력과 같은
펌프였기 때문에 타이핑이 막혔던 것이고, 그래서 출력 경로만 고쳤는데 입력 지연이 250배 줄었다.

부수 효과로 **출력 중 p90(3.9 ms)이 수정 전의 조용할 때 p90(7.7 ms)보다 낮다** — 메시지 홍수가
사라지자 펌프 자체가 한산해졌다.

### 스모크 (성능이 아니라 정확성 — 재시작 직후 16/16 pass)
`Channel<Response>` 전환이 실제로 화면에 그려지는가(여기가 깨지면 터미널이 통째로 빈 화면),
페이로드가 정말 ArrayBuffer인가, 에코 왕복, 합치기 실작동(청크 p50 17KB), `term_resize` 반영
(셸에게 `$Host.UI.RawUI.WindowSize.Width`를 직접 물어 확인), **EOF 직전 마지막 출력 유실 없음**,
`term_close` 후 세션 회수, 재시작 후 탭 13개 복원.
