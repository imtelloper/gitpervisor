## 1. 요구사항

사용자 요청 원문은 "사이드바 프로젝트 행 배경색이 프로젝트마다 비슷해서 구분이 안 된다. 전부 다르게
제대로 해달라"이다. 28은 색을 **넣는** 문제를 풀었고, 36은 색이 **서로 달라 보이는** 문제를 푼다.

받아들이는 조건:

- 등록 프로젝트가 **26개일 때 26색이 전부 서로 다르다** — 완전히 같은 색(ΔE00 0.00)인 쌍이 0개다.
- 임의의 두 프로젝트가 **6종 내장 테마 전부에서** 지각적으로 갈린다: `max(배경 ΔE00, 스트라이프 ΔE00) ≥ 5`
  ("명백히 다른 색" 문턱)인 쌍이 100%.
- 행 위 글자 대비가 **그 테마의 선택 행(`bg-selection`) 위 대비보다 나빠지지 않는다** — 28이 세운 상대
  기준선을 승계한다. 여기에 **절대 하한**을 더한다: `fg ≥ 4.5` / `fg-muted ≥ 3.0` / `fg-dim ≥ 2.0`.
- 검사 대상은 `text-fg` 셋이 아니라 행 위에 실제로 얹히는 **8토큰 전부**
  (`fg` `fg-muted` `fg-dim` `mod` `add` `untrk` `danger` `accent`), 32슬롯 전수.
- **테마별 하드코딩 상수 0개.** 커스텀 테마(태스크 29)로 만든 테마도 내장 6종과 같은 코드 경로로 색을 얻고,
  같은 대비 보증을 받는다.
- 같은 프로젝트의 사이드바 행·모아보기 칩·셀 헤더가 **같은 색**이다(28의 조건 승계).
- 드래그 재정렬·"변경 있는 프로젝트 위로"를 켜고 꺼도 색이 안 바뀐다(28의 조건 승계).
- 프로젝트를 하나 추가할 때 **따라 움직이는 다른 프로젝트의 색이 최소**다.
- 선택 행과 hover 행이 26색 어디 위에서도 읽힌다.

## 2. 현황(근거)

### 2.1 28이 남긴 것 — 유지하는 골격

28은 `src/lib/project-color.ts`를 신설해 "색의 정의가 한 곳"이라는 구조를 세웠고, 그 구조는 이 문서가

## 3. 설계

색을 만드는 방식을 네 가지로 바꾼다. 각 결정마다 무엇을 버렸는지 함께 적는다.

### 3.1 결정 1 — 슬롯 12 → 32, 선형 탐사 → 이중 해싱

`PROJECT_HUES`를 32개로 늘린다(`project-color.ts:26-29`). 26개가 **중복 없이** 들어가고, 슬롯이 남는다.

균등 11.25° 분할이 아니다. 실제 간격은 6~16°로 흔들린다(최소 158→164 = 6°, 최대 164→180 = 16°와
279→294 = 15°). 6종 테마에서 **동시에** CIEDE2000 최소 쌍거리를 최대화하도록 고른 좌표이고, 초록 구간은
눈이 덜 갈려 간격을 벌렸다. 다크에서는 인접 hue가 `i % 2` 명도(2톤)로도 갈리므로 6° 간격이 그대로
지각 거리가 되지는 않는다.

탐사는 이중 해싱(`project-color.ts:181-188`):

```
u    = 해시 >>> 0
pref = u % 32                       // 하위 5비트
step = 1 + 2 * ((u >>> 5) % 16)     // 1,3,5,…,31 — 항상 홀수
slot = (pref + i * step) % 32
```

**step이 홀수여야 하는 이유**: N=32는 2의 거듭제곱이라 홀수만 32와 서로소다. `gcd(step, 32) = 1`이면
`(pref + i·step) mod 32`가 i=0..31에서 32칸을 **전부** 방문한다 — 빈 칸이 있는데 못 찾는 경우가 원리적으로
없다. 짝수 step이면 주기가 32/gcd로 줄어 절반 이하만 훑는다. `pref`와 `step`이 해시의 서로 다른 비트를
쓰는 것(`u >>> 5`)은 같은 pref끼리 같은 step으로 몰리지 않게 하기 위함이다.

효과(설계 단계 200회 측정): 추가 시 색이 따라 움직이는 개수 **5.63 / 최악 11 → 1.04 / 최악 5**.

**버린 것**: 슬롯 배정의 localStorage 영속화(`gp:project-hue`). 28 §8 ③의 미결 질문이었는데, churn이
1.04로 떨어지자 영속화가 사는 값이 거의 없어졌다. 영속화는 "지우는 자리를 하나 더 기억해야 하는" 상태를
늘리고(프로젝트 제거·이름 변경·다른 창), 그 대가로 사는 것이 평균 1개의 색 이동이다. 넣지 않는다.

### 3.2 결정 2 — 알파 틴트를 버리고 불투명 OKLCH. 색은 **JS가 `#rrggbb`로 계산**한다

§2.4의 벽은 알파 축을 없애야 넘는다. 행 색을 패널 위 반투명 틴트가 아니라 **불투명한 한 색**으로 만든다.
그러면 명도와 채도가 독립 노브가 되고, 대비는 명도가, 구분은 채도·색상이 맡는다.

색 공간은 OKLCH를 쓴다 — 같은 L에서 hue를 돌려도 지각 명도가 일정해서, "32색이 전부 같은 대비 밴드
안에 있다"를 명도 한 값으로 관리할 수 있다. HSL로는 불가능하다(같은 L%에서 노랑과 파랑의 휘도가 크게
다르다).

**CSS `oklch()`를 쓰지 않는 이유가 이 설계의 핵심이다.** CSS에 `oklch()`를 적으면 sRGB 게멋 밖 색을 어떻게
끌어당길지가 **브라우저(WebView2/WebKit) 몫**이다. chroma-reduce와 per-channel-clip은 다른 색을 내는데,
어느 쪽이 칠해졌는지 코드가 모른다 → **대비 증명이 성립하지 않는다.** 그래서:

- `maxC(L, h)`(`project-color.ts:64-73`)가 그 L·h에서 sRGB 안에 드는 최대 채도를 22회 이분탐색으로 직접 찾고,
- `oklchHex`(`:75-79`)가 OKLab→선형 sRGB→전달함수→**8비트 반올림**까지 마쳐 `#rrggbb`를 확정한다.

외부 의존성은 0이다(변환 행렬 직접 구현, 약 40줄).

채도 상한 `CAP = 0.11`(`:31`)을 씌운다 — 게멋 최대는 hue별로 3.75배까지 벌어져서, 안 씌우면 노랑만 형광이고
파랑은 흐린 팔레트가 되어 "한 시스템"으로 안 보인다. 실제 사용 채도는 `min(CAP, 0.95 · maxC(L,h))`이고,
0.95 계수는 클램프 경계에서 물러나는 여유다.

**버린 대안**: 안 2 — CSS `oklch(L 0.26 H)` + 알파 유지, 13 hue × 2 명도. 위 게멋 매핑 의존이 killShot이었고,
알파를 남긴 탓에 커스텀 테마가 `selection`을 상속하면 판정이 통째로 무너지는 문제가 따라왔다.

### 3.3 결정 3 — 행 명도를 **테마 토큰에서 이분탐색으로 유도**한다

불투명색으로 옮기면 "그 테마에서 행 명도를 얼마로 할 것인가"가 새 질문이 된다. 테마마다 상수를 박으면
커스텀 테마(태스크 29)에는 해가 없다 — 사용자가 만든 테마는 그 상수 표에 없다.

그래서 상수를 안 박고 **유도**한다(`project-color.ts:129-145`):

```
rowOk(L, floors) = PROJECT_HUES 32개 전부에 대해
                   oklchHex(L, min(CAP, .95·maxC(L,h)), h) 배경을 만들고,
                   8토큰 전부가  (a) 그 테마의 선택 행 위 대비 이상
                                (b) floors면 FLOORS(4.5/3.0/2.0) 이상
L0raw = edge(L => rowOk(L, true),  dark)      // 1단계
     ?? edge(L => rowOk(L, false), dark)      // 2단계 — FLOORS 포기
L0    = L0raw ?? oklabL(panel) ± 0.07         // 3단계 — 패널에서 떼기
```

`edge(pred, up)`(`:92-102`)는 `pred`가 참인 구간의 극단 L을 14회 이분탐색으로 찾는다. `up=true`면 통과하는
가장 큰 L, 아니면 가장 작은 L. 시작 앵커(L=0.02 또는 0.999)가 이미 실패하면 즉시 `null`이다.
다크는 `up=true`로 밝은 쪽 끝을 찾고 `−MARGIN`으로 물러나며, 라이트는 `up=false`로 어두운 쪽 끝을 찾고
`+MARGIN`으로 물러난다 — **항상 안전한 쪽으로** 후퇴한다.

#### 왜 이분탐색이 정답인가 — 대비 증명의 논리

1. WCAG 대비비는 `(L1+.05)/(L2+.05)`이므로 **배경 휘도에 대해 단조**다. 전경 토큰을 고정하면 배경을 한쪽으로
   밀수록 대비는 단조로 오르거나 내린다.
2. 따라서 "32슬롯 × 8토큰이 전부 통과하는 L"의 집합은 **단일 구간**이 된다. 6종 내장 테마 + §7의 합성
   커스텀 테마 5종 전부에서 0.005 스텝 스캔으로 확인했다(통과↔불통과 전환 횟수 1).
3. 단일 구간이면 이분탐색이 정확하고, **최악 hue는 정의상 그 구간 끝에 붙는다.** hue를 따로 탐색할 필요가
   없다 — 극단 L에서 통과했다면 그 구간 안의 모든 L에서 32 hue 전부가 통과한다.
4. 다크의 tone1(`L0 − TONE_D`)은 **더 어두워 대비가 올라가므로** 검사 대상이 아니다(`:128` 주석).
   2톤이 대비 예산을 한 자리도 쓰지 않는다.

이 논리 덕분에 **테마별 값은 0개**이고, 팔레트를 튜닝하는 이름 붙은 노브는 4개(`CAP` `TONE_D` `MARGIN`
`STRIPE_D`)로 줄어든다. 이름이 없는 계수·폴백이 몇 개 더 있으니 튜닝 전에 §4.1의 두 번째 표를 함께 본다.
입력이 테마 토큰 18개뿐이므로 내장 6종·커스텀·미지의 id가 전부 같은 경로를 탄다.

> 엄밀히는 `rowOk` 안의 채도가 `min(CAP, 0.95·maxC(L,h))`로 L을 따라 같이 변하므로, 대비가 L에 완전 단조라는
> **수학적** 보장은 없다. 위 3번은 스캔으로 확인한 경험적 사실이고, e2e 19의 32×8 전수 측정이 사후 방벽이다
> (§7.2). 유도가 어긋나면 스위트가 FAIL한다.

**절대 하한 `FLOORS`(`:38`)를 왜 따로 두는가**: "기준선(선택 행) 이상"만 보면 **기준선 자체가 무너진 커스텀
테마에서 같이 무너진다.** 실측(light 토큰 + `panel #ffffff` + `selection #3574f0`): 하한만 빼고 같은 유도식을 돌리면 fg **3.75** /
muted **1.72** / dim **1.20**까지 내려가면서 "기준선은 넘었다"며 PASS를 보고한다. 하한을 넣으면
6.74 / 3.09 / 2.16이다(§9.6 케이스 A).

> ⚠ 코드 주석(`project-color.ts:36-37`)과 §3.5 안 1 행에 적힌 **3.99 / 1.83 / 1.28**은 이 값이 아니다 —
> 심사 **안 1**(테마별 L0 상수·단일 톤)에서 잰 수치이고, 현 유도식에서 FLOORS만 뺀 재계산은 위의
> 3.75 / 1.72 / 1.20이다(2026-09-04 재현). 그 코드 주석을 다음에 손댈 때 함께 고칠 것.

**다크/라이트 판정은 base id가 아니라 실제 팔레트로 한다**(`:123`):
`contrastRatio(c.fg, "#000000") >= contrastRatio(c.panel, "#000000")`. §2.6의 `TINT[t.base]` 버그가 여기서
원천 소멸한다.

**버린 대안**: 안 3 — HSL 70% + 명도 티어 3단을 라이트까지 적용. 라이트에 티어를 주면 **오히려 악화**한다
(라이트 최소 ΔE00 0.82). 흰 패널 위에 명도 예산이 없다는 물리적 사실을 티어로 이길 수 없다.
그래서 티어(2톤)는 **다크에만** 이식하고 라이트는 1톤이다(`:155`).

### 3.4 결정 4 — 좌측 4px 스트라이프

라이트 2종에는 배경만으로 넘을 수 없는 천장이 있다. 흰 패널 위에서 행 명도를 아무리 조정해도 32색의 최소
지각 거리가 **1.7~2.2**에 그친다(다크는 6.0+). 명도 예산이 없기 때문이다 — §3.3의 유도가 L을 0.92 근처로
밀어 올리는데, 그 밴드에서 쓸 수 있는 채도가 얼마 안 남는다.

그래서 **글자가 얹히지 않는 면**을 하나 만든다. 행 왼쪽에 4px 띠를 두고(`ProjectItem.tsx:110-118`),
이 띠는 비텍스트 대비 3:1만 받으면 되므로 **채도를 게멋 끝까지 민다**(`CAP` 없이 `maxC` 전량,
`project-color.ts:149-152`). 문턱은 3.05로 3.0에 0.05 여유를 뒀다.

결과: 라이트 8.03 / solarized-light 7.02 (실측 §9.3). 라이트에서 프로젝트를 구별하는 주체가 배경에서
**띠로 넘어간다.**

스트라이프는 다크·라이트 **양쪽 모두 2톤**이다(`STRIPE_D = 0.105`) — 두 톤 다 패널 반대쪽으로 가므로
라이트에서도 명도 예산 문제가 없다.

**선택 표시를 accent 색 하나에 못 맡기는 이유**: accent와 스트라이프 32색의 최소 ΔE00이 darcula **4.86**,
solarized-light **4.65**로 문턱 5 아래다(§9.4). "선택 안 한 행이 선택된 것처럼" 보일 수 있다. 그래서 선택 큐를
**폭 4→8px(크기 축) + accent outline** 이중 단서로 뒀다. 옛 `border-l-2 border-accent`는 스트라이프가 그
자리를 쓰므로 삭제한다.

**버린 대안**: 안 4 — 12 hue × 3 tone = 36 불투명색 + 패턴 3종. 라이트 배경 최소 ΔE00 2.14로 안 3과 같은 벽에
부딪혔고(→ 스트라이프만 이식), 절대 하한이 없어 커스텀 테마에서 동반 붕괴했다. 패턴(사선·점·격자)은
사용자가 **암기해야 하는 토큰**이라 "배경색을 다르게 해달라"는 요청에 대한 답으로는 과설계라고 판단했다.

| 안 | 무엇 | 버린 이유 / 이식한 것 |

### 4.2 캐시 키에 **토큰 서명**이 들어가는 이유

```ts
const key = `${themeId}|${JSON.stringify(c)}`;   // :118 — 조회는 토큰 해석 뒤에
```

테마 id만 키로 쓰면 안 된다. 커스텀 테마 편집은 `stores/customThemes.upsert`가 **같은 id를 교체**하므로
(`cur.map(x => x.id === t.id ? t : x)`) 편집 후에도 옛 팔레트가 영원히 나온다. 모듈 스코프 `Map`이라
창을 새로고침하기 전까지 복구되지 않고, 다크 테마를 라이트로 편집하면 흰 패널 위에 어두운 행이 남아
**이 설계의 대비 보증이 통째로 무효**가 된다. 토큰 값까지 키에 넣으면 정의가 바뀐 순간 자동으로 미스가
난다. 내장 6종은 토큰이 불변이라 언제나 히트한다. (§9.4 결함 2 — 실제로 일어났다.)

### 4.3 `useProjectColors`가 구독하는 세 가지

```ts
const { data: projects } = useProjects();                                   // :221
const theme = useSyncExternalStore(appliedTheme.subscribe, appliedTheme.get); // :222
const customThemes = useCustomThemes((s) => s.themes);                       // :225
```

`appliedTheme`(`:203-213`)은 `MutationObserver`로 `document.documentElement`의 `data-theme` 속성만 감시하고,
`get`은 `dataset.theme ?? "darcula"`다.

**`settings.theme`이 아니라 `data-theme`을 읽는 이유**: 설정 › 모양의 라이브 프리뷰
(`src/components/settings/SettingsDialog.tsx:172-176`의 `previewTheme`)와 커스텀 테마 편집기는
**저장값을 건드리지 않고** `dataset.theme`를 바꾼다(다이얼로그 로컬 form의 `update("theme", id)`와
`refreshTerminalThemes()`도 함께 부르지만, 영속되는 `settings.theme`은 그대로다).
저장값을 읽으면 프리뷰 중 **행 색만** 이전 테마에 얼어붙는다 — 다이얼로그가 반투명 스크림이라 사이드바가
그대로 보이므로 즉시 눈에 띈다(§9.4 결함 1). 옛 CSS 변수 구현은 셀렉터가 `data-theme`를 직접 따라가서
이 문제가 없었다 — **값을 JS로 옮긴 대가를 여기서 갚는다.**

**`customThemes`까지 구독하는 이유**: 커스텀 테마 편집은 id를 보존하므로 `theme` 문자열이 안 바뀐다.
`data-theme` 감시만으로는 편집·삭제·다른 창의 storage 변경이 안 내려온다.

첫 페인트는 `main.tsx:49-50`(`localStorage.getItem("gp:theme")` → `dataset.theme` 선주입, 기존 코드)이 이미
해결해 둔다 — 렌더 전에 심어 두므로 첫 프레임 값으로도 `dataset.theme`가 맞다.

## 7. 검증

### 7.1 e2e 14 `#12` — 인라인 변수와 "칩 == 행"

```js
// 14-frontend-dom.mjs:902-907
const rowTint = await cdp.eval(`${rowExpr}?.style.getPropertyValue('--tint') ?? ''`);
const rowBg = await bgOf(rowExpr);
r.check(
  "사이드바 행: --tint 인라인 변수 + 배경 실제 적용(bg-(--tint) 규칙 생성)",
  /^#[0-9a-f]{6}$/.test(rowTint.trim()) && !!rowBg && rowBg !== "rgba(0, 0, 0, 0)",
  `tint=${rowTint} bg=${rowBg}`,
);
```

정규식만 바뀌었다(옛 판: `/^hsl\(\d+ 70% var\(--proj-l\) \/ var\(--proj-a-row/`). 체크 이름과 `rowBg` 판정은
그대로 — **불변식은 "인라인 변수가 Tailwind 규칙을 만들어 실제로 칠해진다"**이고, 바뀐 것은 값의 형식뿐이다.
Tailwind가 조립 클래스를 스캔 못 해 배경이 투명인데 tsc는 통과하는 유형을 이 단언이 잡는다.

**칩 == 행 단언(`:918-923`)은 유지한다.** 이것이 "같은 프로젝트 = 같은 색"의 **유일한 회귀 방지**다.
색 계산이 한 모듈에 있어도 소비 지점이 5곳(사이드바 + 모아보기 4곳)이라, 한 곳이 다른 값을 쓰기 시작해도
타입·빌드·나머지 단언은 전부 통과한다. 알파가 사라져 이제 `rgb3` 비교가 사실상 완전 일치 비교다.

신설 단언(`:909-913`) — 이중 해싱이 32칸을 전부 방문한다는 성질을 직접 겨눈다:

```js
const uniq = await cdp.eval(`(()=>{const a=window.__gpv.projectColor;
  const n=Array.from({length:32},(_,i)=>'zz'+i);
  return new Set(a.assignProjectSlots(n).values()).size;})()`);
r.check("32개 이름 → 슬롯 중복 0", uniq === 32, `unique=${uniq}`);
```

step이 짝수가 되는 회귀나 슬롯 수 축소가 여기서 즉시 실패한다.

### 7.2 e2e 19 — 앱 함수를 직접 부른다

```js
// 19-themes.mjs:146 (발췌)
const pal = pc.projectPalette(document.documentElement.dataset.theme || 'darcula');
```

**여기서 팔레트를 재구현하면 안 된다.** 사본은 구현이 바뀌어도 조용히 통과한다 — 옛 판이 12 hue를
하드코딩하고 있었다(§2.5). 대비 계산식(WCAG)만 페이지 안에 다시 적는다(`:113-115`): 앱의 `contrastRatio`를
그대로 쓰면 대비식 자체의 버그가 양쪽에서 상쇄된다. **팔레트는 앱 함수, 대비식은 독립**이 이 스위트의 계약이다.

측정 토큰·절대 하한·슬롯 수도 **전부 다리에서 읽는다** — 스위트에 손사본이 하나도 남아 있지 않다.

```js
const pc = window.__gpv.projectColor, T = pc.FG;        // 옛 판: T=['fg', … ] 손사본
out.floors = pc.FLOORS;                                  // 옛 판: 4.5/3.0/2.0 하드코딩
out.hues   = pc.PROJECT_HUES.length;                     // 옛 판: c.n === 32
```

**슬롯 수 핀은 19가 아니라 14에 있다.** `projectPalette`가 `PROJECT_HUES.map(...)`이라
`pal.length ≡ PROJECT_HUES.length`가 **구조적으로 항상 참**이다 — 19의 `c.n === c.hues`는
팔레트↔hue 정합 검사일 뿐 슬롯 수 변경을 원리적으로 감지하지 못한다(실측: 32→31로 줄여도
19는 `n=31/31`로 ALL GREEN). 수를 무는 자리는 `14-frontend-dom.mjs` 한 곳이다:

```js
const slots = await cdp.eval(`… { uniq:new Set(a.assignProjectSlots(n).values()).size, hues:N } …`);
r.check("N개 이름 → 슬롯 중복 0", slots.uniq === slots.hues && slots.hues > 0, …);  // 배정 품질 (N은 다리에서)
r.check("슬롯 수 == 32 (ΔE00 > 5 보증 — 축소·확대 양방향)", slots.hues === 32, …);
```

32는 이 저장소에서 **의도적으로 박은 유일한 슬롯 상수**다(§3.1의 ΔE00 > 5 최소 슬롯 수). `>=`가 아니라 `===`인 이유는 늘리는 것도 안전하지 않기 때문이다 — hue 간격이 좁아져 ΔE00 보증이 깨진다. 줄이면
여기서 걸리고, 늘릴 때는 이 줄을 함께 고치는 것이 의도 표명이다. 옛 판은 14에도 `length:32`·
`uniq === 32` 손사본이 있어 **축소만** 우연히 잡고 확대는 아무도 안 잡았다.

```js
// 하한 0(mod/add/untrk/danger/accent)은 자동 통과 — 구현이 "의도적으로 하한 없음"으로 0을 박아 뒀다.
const okAbs = Object.entries(c.floors).every(([k, min]) => c.worst[k] >= min);
const okRel = Object.keys(c.baseline).every((k) => c.worst[k] >= c.baseline[k] - tol);
r.check(
  `[${id}] 프로젝트 색 — ${c.n}슬롯 × ${nTok}토큰 ≥ 기준선 − ${tol} · 하한(${floorDesc}) · 스트라이프 ≥ 3:1`,
  c.n === c.hues && okAbs && okRel && c.stripe >= 3.0, …);
```

`r.check` 문구의 슬롯 수·토큰 수·하한 값도 실측치에서 만든다. 문구가 값과 따로 놀면 다음 사람이 오독한다.

**컴파일 타임 강제가 짝을 보증한다.** `FG`는 `as const satisfies readonly ThemeToken[]`이라 `themes.ts`
`THEME_TOKENS`에 없는 토큰을 넣으면 막힌다(오타형은 TS2820 "Did you mean …?", 그 밖은 TS2322).
`FLOORS`는 `Partial<Record<string, number>>`에서 **`as const satisfies Record<(typeof FG)[number], number>`
(FG 전수)**로 바뀌어, `FG`에 토큰을 추가하는 순간 TS2741(키 누락)로 컴파일이 깨진다 — 하한 없는 토큰이
조용히 끼어들 수 없다. 타입 **표기**(`: Record<…>`)가 아니라 `satisfies`인 이유는 초과 키(오타) 차단이
fresh 객체 리터럴에만 걸리는 검사(TS2353)라, 나중에 스프레드 조립이나 별도 변수 경유로 리팩터하면
표기형은 누락만 남고 오타를 놓치기 때문이다. `projectPalette`의 `c`도 `Record<string, string>` →
**`Record<ThemeToken, string>`**으로 좁혀 `c[k]` 사용처에 같은 제약이 걸린다(2중 방어 — `FG`의
`satisfies`를 누가 지워도 사용처가 잡는다). `rowOk`의 `FLOORS[k] ?? 0`도 `FLOORS[k]`로 정리됐다
(하한 없음은 이제 명시적 `0`이다).

**`FLOORS`는 단언값이자 이분탐색의 입력이다 — 값을 올려도 e2e는 통과하는 게 정상이다.**
`rowOk`가 `FLOORS`를 읽고 그 `rowOk`로 행 명도를 이분탐색하므로, **도달 가능한** 값으로 올리면
팔레트가 따라 어두워져 하한을 맞춘다(실측: `fg` 4.5→9.9에서 darcula worst fg 7.70→**10.20**으로
이동, ALL GREEN). 이걸 "가드가 죽었다"로 오진하지 마라. `okAbs`가 실제로 무는 것은 이분탐색이
해를 못 찾아 무하한 폴백(`L0raw` 2단계)으로 떨어질 때뿐이다 — **돌연변이 검증은 `fg: 21`로 한다**
(실측: 6/6 테마 FAIL, `41 pass / 6 fail`). `FG` 쪽 돌연변이는 `"warn"` 추가 + `FLOORS.warn: 9.9`가
라이트 2종에서 FAIL(`45 pass / 2 fail`)하며, 문구가 `9토큰`·`warn≥9.9`로 따라 바뀐다.

**타입이 강제하는 것은 키의 존재이지 값의 의미가 아니다.** `FG`에 토큰을 추가하다 컴파일 오류를 보고
`newtok: 0`을 복붙하면 "하한 없음"이 조용히 복원된다(0은 설계상 허용값이라 판정에 넣을 수 없다).
그래서 19의 detail에 `floors0=<하한 0인 토큰 수>`를 함께 찍는다 — 리포트에 흔적이 남는다.

**다리가 없으면 조용히 통과하지 않는다.** 스위트 진입부에 `__gpv.projectColor` 다리(FG·FLOORS·PROJECT_HUES)와
`__gpv.builtinTokens` 확인 체크가 있고, 없으면 **FAIL**한다. 값을 전부 구현에서 읽어 오는 구조에서는 다리가
빠졌을 때 "빈 목록을 다 돌았다"로 만점이 나기 때문이다(잰 척). 실측: `delete __gpv.projectColor.FG` 후 19를
돌리면 `40 pass / 1 fail`.

THEME_IDS(내장 6종 목록)도 손사본을 없애고 `Object.keys(__gpv.builtinTokens)`에서 읽는다 —
`BUILTIN_TOKENS`가 `Record<ThemeName, …>`이라 `THEMES`에 테마가 늘면 키도 컴파일 타임에 따라 늘어난다.

### 7.3 실기 체크리스트

1. **팔레트가 실제로 그려지는가**(CDP, 6종 전부) — 행 배경·스트라이프 배경을 수집해 **전부 서로 다른가**.
   정적 계산은 8비트 반올림을 가정했을 뿐이고 실제로 칠해지는 값은 WebView2가 정한다.
2. **계산값 == 화면 픽셀** — 스크린샷을 raw RGB로 샘플링해 `projectPalette` 값과 대조. CSS 파이프라인
   (합성·색 관리)이 값을 바꾸지 않는지.
3. **첫 페인트 플래시** — `gp:theme = monokai` 상태로 앱 재시작, 100ms/300ms 스크린샷. 첫 프레임이 darcula
   팔레트면 `dataset.theme` 폴백이 안 먹은 것.
4. **모아보기 별도 창의 칩 == 메인 창 행** — 알파가 없으니 이제 문자열이 완전히 같아야 한다.
5. **육안, 등록 프로젝트 전체를 한 화면에**(6종) — (a) 인접 행이 갈리는가, (b) **라이트 2종은 배경이 거의 안 갈리는 것이 설계상
   정상** — 띠가 갈리는지가 판정 기준이다(§6), (c) 4px 띠가 2·3행이 빈 58px 행에서도 보이는가.
6. **선택·hover 큐** — darcula/solarized-light에서 accent와 가까운 스트라이프 슬롯(ΔE00 4.65~4.86)을 선택해
   보고 **선택 안 한 행이 선택된 것처럼 보이지 않는지**. hover 링(fg-muted)이 가장 밝은 슬롯 위에서 보이는지.
7. **`.ai-working` 행** — 알파 .19에서 작업 중 표시가 여전히 눈에 띄는지, 그 행의 텍스트가 읽히는지(다크 4종).
8. **커스텀 테마 함정 케이스** — 기반 **Light**로 커스텀 테마를 만들고 `panel`만 `#ffffff`로. 행 글자가 읽히는지.
   ⚠ 이 1단계를 **기반 Darcula**로 하면 fg 1.04 / fg-muted 2.09다 — darcula의 밝은 `fg #dfe1e5`가 흰 panel 위에
   오는 테마라 하한을 만족하는 L이 존재하지 않아 §3.3 3단계 폴백을 탄다. 폴백은 FLOORS를 보증하지 않으며
   애초에 앱 전체가 못 읽는 테마다. **결함이 아니다.**
9. **배정 안정성** — 프로젝트 1개 추가 전후 배경색을 수집해 색이 바뀐 기존 프로젝트 수를 센다.
10. **33번째 경계** — 33개까지 늘려 중복이 **정확히 1쌍**인지.
11. **성능** — `projectPalette` 첫 호출이 20ms 미만인지(메모 이후 0).

### 7.4 ⚠ 설계 문서 §A의 팔레트 hex 표를 회귀 기준선으로 쓰지 마라

**어떤 hex 표도 회귀 기준선이 아니다. 기준선이 필요하면 e2e 19처럼
`window.__gpv.projectColor.projectPalette(<theme>)`를 직접 불러 재라.** 그래서 **이 문서에도 색값 표를
싣지 않는다** — 표를 비교하면 정상 동작을 "팔레트가 어긋났다"고 오진한다.

근거: 설계 단계 명세(`SPEC.md` §A)에 6테마 × 32슬롯 × bg/stripe = 384개 hex 표가 있었는데 **실제 구현과
127개가 다르다.** 프로토타입(`s7.mjs`)과 구현이 이분탐색 종료 L에서 <0.002 어긋난 계통 반올림 차이이고,
방향은 테마별로 일정하다(darcula 배경 26/32, light 스트라이프 22/32, solarized-light 배경 23/32).
차이는 **대부분 채널 ±1이지만 전부는 아니다 — 최대 채널 차 3**(예: `light` 스트라이프 슬롯 1,
명세 `#ff1d64` vs 구현 `#ff2065`, Δ[0,3,1]. 2026-09-04 재현). 지각 차이는 0이고 대비·ΔE00 판정은 전부
동일하게 통과한다. L0·스트라이프 L 표는 ±0.001로 일치한다.

> ⚠ **그 `SPEC.md`는 이 레포에 없다.** 작업 세션의 스크래치패드 산출물이라 세션과 함께 사라진다
> (`%TEMP%\claude\<세션>\scratchpad\SPEC.md`, 경고는 그 파일 `:257-263`). 즉 "명세에 경고를 넣었다"는
> 완화책은 **오래 살지 않는다** — 이 절이 유일하게 남는 기록이다. 팔레트 좌표(`PROJECT_HUES` 32개)를
> 재최적화한 스크립트도 남아 있지 않으므로, hue를 다시 고르려면 §3.1의 목적함수(6종 테마에서 동시에
> CIEDE2000 최소 쌍거리 최대화)로 **처음부터 다시 풀어야 한다.**

### 9.9 정적 검증이 통과했는데 실기가 잡은 결함 2종

> 이 둘은 `tsc` 0, `npm run build` 0, e2e 13·14·19 전부 PASS, 스크린샷 정상인 상태에서 살아 있었다.
> 잡아낸 것은 **앱 안에서 실제로 테마를 눌러 본 것**과 **같은 id로 커스텀 테마를 두 번 저장해 본 것**뿐이다.
> CLAUDE.md `## 검증`이 경고하는 유형("컴파일 통과·테스트 통과·CI success인 채로 배포까지 나갈 뻔한 결함")의
> 교과서적 사례다.

#### 결함 1 — 테마 라이브 프리뷰 동결 (옛 코드 대비 **회귀**)

- **증상**: 설정 › 모양에서 테마를 클릭하면 패널·토큰은 즉시 바뀌는데 **프로젝트 행만 이전 테마 색으로
  얼어붙는다.** monokai→light 프리뷰 실측: 패널 `#ffffff`인데 행은 `rgb(3,47,45)` 유지 → 그 위 light `fg #222429`
  대비 **1.00~1.07**(프로젝트명이 사실상 안 보인다). 설정 다이얼로그는 `bg-black/50` 스크림이라 사이드바가
  뒤에 그대로 보인다(`src/components/settings/SettingsDialog.tsx:277`).
- **원인**: `previewTheme`(`src/components/settings/SettingsDialog.tsx:172-176`)는
  `document.documentElement.dataset.theme`를 바꾸고 다이얼로그 로컬 form(`update("theme", id)`)과
  터미널 테마(`refreshTerminalThemes()`)를 갱신하지만, **영속되는 `settings.theme`은 건드리지 않는다.**
  그런데 최초 구현이 `settings?.theme`를 **먼저** 읽었다
  (명세 스니펫 `settings?.theme ?? dataset.theme ?? "darcula"` 그대로).
- **왜 조용했나**: 옛 구현은 `hsl(h 70% var(--proj-l)/var(--proj-a-row))`라 **CSS 변수가 `data-theme`를 자동으로
  따라갔다.** 색 계산을 CSS→JS로 옮기면서 "테마를 어디서 읽는가"가 처음으로 **선택 사항**이 됐고, 저장값을
  고르는 순간 프리뷰 경로만 끊겼다. 타입 통과, 빌드 통과, e2e 19는 **저장된 테마로만** 전환하므로 이 경로를
  아예 밟지 않는다.
- **수정**: `dataset.theme`를 `useSyncExternalStore` + `MutationObserver`로 구독(`project-color.ts:17, 203, 222`).
  `useSettings()` 의존 자체가 사라져 "저장값 우선" 순서 버그가 원천 소멸했다. 대안으로 제안됐던
  `stores/ui.ts previewThemeId`는 리셋 자리를 3곳 기억해야 하고 커스텀 테마 편집기 프리뷰는 여전히 못 잡아
  채택하지 않았다.
- **검증**: 기계 경로 `dataset.theme='light'` → 24/24 행 전환(수정 전 `row bg followed theme: false` → `true`),
  실사용 경로 설정 › 모양 '라이트(IntelliJ)' 실클릭 → 행·스트라이프 갱신, Esc → 원복.

#### 결함 2 — 팔레트 캐시 미무효화 (정적 검증 2회 + 실기 1회, **3중 발견**)

- **증상**: 커스텀 테마를 **편집**하면 다른 토큰은 전부 새 색인데 **프로젝트 행만 편집 전 팔레트**로 남는다.
  앱을 재시작해야 복구된다. 다크 커스텀 테마를 라이트로 편집 → fg 최악 대비 **12.25 → 1.07**(fg-muted 1.42) 붕괴.
  재현 로그 `{editBefore:#fedde6, editAfter:#fedde6, sameColorsFreshId:#e991ad, staleBug:true}` — 같은 색을
  **새 id**로 계산하면 다른 값이 나오는데 편집한 테마는 옛 값을 유지한다.
- **원인**: 모듈 스코프 `Map`이 **테마 id만** 키로 썼는데, 편집은
  `setEditing({draft:t})` → `customThemeCss({...})` → `upsert(t)` → `cur.map(x => x.id === t.id ? t : x)`로
  **id를 보존**한다. 캐시 조회가 토큰을 읽기 **전에** 조기 반환했다. `installCustomThemeStyles()`가 CSS는
  재생성하지만 이 캐시는 안 건드린다.
- **왜 조용했나**: **명세 스니펫 자체가 캐시를 그렇게 정의했다** — 구현은 명세에 충실했고, 명세 단계의 구멍이다.
  게다가 사용자에게 커스텀 테마가 하나도 없어(`gp:custom-themes = "[]"`) 화면에 드러나지 않는 잠복 결함이었다.
  노출 심볼이 `[PROJECT_HUES, projectPalette, assignProjectSlots]`뿐이라 **무효화 수단 자체가 존재하지 않았고**,
  `projectPalette(id)`가 동일 배열 참조를 돌려준다는 것이 유일한 단서였다. 이 설계의 **핵심 보증**
  ("명도를 테마 토큰에서 유도해 대비를 보장한다")이 통째로 무효가 되는 자리다.
- **수정**: 캐시 키에 토큰 서명을 넣어 **자기 무효화**시켰다(§4.2, `project-color.ts:118-120, 162`).
  신규 export 0건 — `clearPaletteCache`는 만들지 않았다(§3.6).
  **캐시만 고치면 리렌더가 없어 화면이 안 바뀌므로**, 결함 1의 `data-theme` 구독 + `useCustomThemes` 구독(`:225`)이
  함께 있어야 닫힌다. **두 결함은 한 파일 안의 두 줄기(무엇을 칠할지의 출처 / 캐시 신선도)로 함께 닫혔다.**
- **검증**: 같은 id로 darcula → light 토큰 재저장 시 24/24 새 팔레트, fg 최악 12.25.

### 9.10 검증에서 잡힌 것 (그 밖)

- **구현 보고의 "팔레트 hex가 명세와 일치한다"는 사실이 아니었다.** 정적 검증자 2명이 각각 독립으로 잡았다
  (전수 대조 + `spec-diff.mjs`) — **hex는 127/384 불일치**다(대부분 채널 ±1, 최대 3 — §7.4). 같은 보고서가 몇 줄 아래에서 "명세 표가
  아주 조금 다른 반올림으로 뽑힌 것 같다"고 **스스로 반대되는 말**을 하고 있었다. 표본만 보고 "일치"라고 쓴 것이다.
  나머지 셋(슬롯 배정표 26/26 · L0 · 최악 슬롯)은 일치가 맞다.
  → **자기 산출물을 명세와 "일치한다"고 보고할 때는 전수 대조를 했는지 먼저 확인하라.**
  화면과의 일치는 별개로 참이다(렌더 픽셀 == 계산값, 최대 ΔE 0.00 — §9.8).
- **명세 실기 항목 8의 기대값이 틀렸다** — 1단계를 '기반 Darcula'로 하면 fg 12.25가 아니라 1.04/2.09다.
  그 12.25의 실제 주인은 케이스 D였다. 명세 쪽 `SPEC.md:441`에 정정 경고를 넣었고(그 파일은 레포에 없다 — §7.4), 코드에도 주석을 추가했다(`project-color.ts:138-141`).
- **`styles.css` 라이트 보정 블록의 주석이 다크 알파를 못 박고 있었다.** 원문(`git show HEAD:src/styles.css:449`)이
  `/* 라이트 테마 보정 — 다크 전제의 **알파 0.26** 무지개·글로우는 …`인데, 그 블록이 실제로 설정하는 값은
  `.13`이고 다크는 이번에 `.19`로 내려갔다. 기능은 정상이지만(CSSOM 파싱 확인) 다음 사람이 그 숫자를 믿고
  고치면 라이트 무지개가 깨진다. **그 한 줄에서 "알파 0.26" 문구만 지웠다**(diff −1/+1). 새로 넣은 근거 주석
  4줄은 다크 `.ai-working` **위**(`styles.css:398-401`)에 있다 — 라이트 셀렉터 안이 아니다.
- **e2e 14 `컬럼 헤더 X 중심 elementFromPoint` 간헐**(4회 중 3회 FAIL) — 제안된 수정이 안 먹었다. 진짜 원인은
  `null` 반환이 아니라 **컬럼이 막 열린 직후의 낡은 X 버튼 rect**였다(그 좌표엔 헤더 요소가 있어
  `closest('button').title`이 undefined → 메시지에 `null`로 찍힘). rect를 매 회 다시 재도록 고쳐 **4회 연속 PASS**.
- **e2e 14 `모아보기 반환 후 PTY 폭 복구` 간헐** — 이것도 제안된 수정(폴링)이 안 먹었다. 원인이 둘:
  (a) 프로브가 `listTerminals().find(status==='live')`로 **사용자가 띄워 둔 20여 개 중 첫 번째**를 집어 남의 셸에
  `Write-Host`를 쏘고 있었다(숨은 탭이라 `term.cols` 233 vs 실제 ConPTY 275), (b) 판정 기준 `want`를 fit 이전
  값으로 잡았다. paneId 고정 + 기준을 현재 xterm 열수로 교체 → **3회 연속 PASS**. **테스트 격리 결함**이었다.
  이로써 `00-INDEX.md:254`의 "14 #2b는 부하 시 기대값 스냅샷 낡음" 원인 추정은 반증됐다.
- `text-fg-dim`이 전 테마에서 4.5:1 아래인 것(monokai 2.92 · darcula 2.12 · nord 2.89 · sol-light 3.45 ·
  light 3.92)은 **결함이 아니다** — 명세 하한 2.0 이상이고 선택 행 기준선(2.81/2.06/2.79/3.34/3.81)보다 항상 낫다.
  용량·"변경 없음"은 의도적 저강조다. 다만 `status.error`만 `fg-muted`로 올렸다(§4.4).

### 9.11 설계 대비 이탈

| 1 | `useProjectColors`가 `settings?.theme` 대신 **`data-theme` MutationObserver 구독** | 명세 스니펫대로 구현했더니 라이브 프리뷰가 얼어붙었다(§9.9 결함 1). `useSettings` 의존을 없애 순서 버그를 원천 제거 |

### 9.12 미검증

- **첫 페인트 플래시**(§7.3 ③) — 앱 재시작이 필요해 돌리지 않았다(사용자가 dev 앱을 계속 쓰는 중).
  `dataset` / `localStorage` / `settings` 3자 일치와 폴백 코드 경로만 확인했다.
- **모아보기 별도 창의 칩 색**(§7.3 ④) — 살아있는 PTY 소유권을 가져가 사용자 작업을 방해하므로 생략.
  **메인 창 안** 모아보기는 완전일치 확인(§9.8).
- **`.ai-working` α .19 육안**(§7.3 ⑦) — 작업 중인 프로젝트가 없어 재현 불가. CSSOM 파싱만 확인.
- **33번째 경계 실기**(§7.3 ⑩)와 **실제 프로젝트 추가·제거 실기**(§7.3 ⑨) — 사용자 등록 목록을 건드려야 해서
  **합성 이름 32/33/34/64개**로 앱 안에서 확인했다. 제거 churn은 재측정하지 않았다(§9.5).
- **커스텀 테마 편집 중(저장 전) 프리뷰**가 행 색에 안 붙는 잔여 틈 — §8 ⑥. 저장 시점에는 따라온다.
- **설계 단계 명세(`SPEC.md`)와 hue 최적화 스크립트가 레포에 없다** — 세션 스크래치패드 산출물이라 사라진다.
  §7.4·§3.1에 필요한 내용은 옮겨 적었지만, 384개 hex 표와 최적화 목적함수의 실행 코드는 재현할 수 없다.
- **전체 e2e 러너** — 13·14·19 부분 실행만 했다. 14의 간헐 2건을 고쳤으므로 `00-INDEX.md:254`의 총계
  603/3/6은 이제 낡았을 가능성이 크나 확인하지 않았다.
